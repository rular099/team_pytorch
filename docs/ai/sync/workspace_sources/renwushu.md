# Codex 任务：TEAM_PYTORCH 项目记忆与跨对话交接体系建设

## 一、背景与目标

Repository：`rular099/team_pytorch`

用户正在 ChatGPT Projects 中长期开展科研工作。由于项目历史很长，已有多个连续对话，需要在不依赖超长聊天上下文的情况下，保持 ChatGPT 对项目目标、进度、实验结果、历史决策的准确理解。

请为该项目建立一套可持续维护、基于 GitHub 的项目记忆与交接系统。

**本任务是文档与工作流工程，不是新一轮模型研发任务。**

最终效果：

1. ChatGPT 在新对话中，读取少量文件即可恢复项目全局上下文。
2. 需要历史信息时，能定位到准确的实验报告、代码、commit 和决策依据。
3. Codex 每轮完成工作后，可以自动或半自动更新项目状态。
4. 不同实验分支的状态互不覆盖。
5. 旧聊天被归档或删除后，项目仍能继续推进。
6. 现有科研代码和实验结果完全不受影响。

## 二、第一阶段：全面审计现有文档

首先检查：

- `AGENTS.md`
- `SESSION_SUMMARY.md`
- `docs/ai/README.md`
- `docs/ai/PROJECT_CONTEXT.md`
- `docs/ai/` 中现有审阅与交接文档
- `reports/` 下的主要实验报告
- Git 分支、tags、近期提交及相关实验线

重点识别：

- 项目的最终科研目标；
- 已经正式确认的技术约束；
- 现有 RT、FE、V01 等实验线；
- 已完成、进行中、暂停和计划中的工作；
- 重要结果及其证据；
- 重要历史技术决策；
- 哪些文档已经过时或存在冲突。

不要假设默认分支包含最新结果。

先执行 Git 状态检查，确认各分支 HEAD。需要读取其他实验分支时，可以使用 Git 原生命令或独立 worktree，但不得覆盖当前工作区。

特别注意：2026-10-06 的 V01 文档不一定是整个仓库的最新状态。

## 三、第二阶段：建立项目记忆文件

建议建立 `docs/ai/memory/` 目录。

### 1. PROJECT_MEMORY.md

保存稳定的长期信息：

- 项目背景和最终目标；
- 输入、输出和主要模型任务；
- 用户对模型架构的长期要求；
- 科学评价原则；
- RT55 等必要兼容性要求；
- 数据泄漏防范；
- ChatGPT、Codex、用户和超算的分工；
- 证据优先级；
- 科研工作的成功标准。

控制文件体积，避免复制整个历史报告。

### 2. CURRENT_STATUS.md

这是新对话最重要的状态入口。

必须包含：

- 更新时间；
- 状态生成时的 Git commit；
- 每条实验线的 branch 和对应 commit；
- 当前状态；
- 最近已核验的主要成果；
- 尚未解决的核心问题；
- 下一步任务；
- 相关报告位置。

实验线必须独立记录。

不能简单将某一个分支的 HEAD 当作整个项目的 HEAD。

状态建议使用：

`verified_complete`、`in_progress`、`planned`、`blocked`、`superseded`、`unknown`。

其中 `unknown` 是缺少证据，不能等同于尚未完成。

### 3. DECISION_LOG.md

为重要技术决策建立编号。

每条记录应包含：

- 决策 ID；
- 日期；
- 实验线；
- 问题背景；
- 讨论过的选项；
- 最终决定；
- 支持该决定的证据；
- 适用范围；
- 后来是否被推翻；
- 来源文件和 commit。

特别记录重大架构取舍、评估协议、消融设计以及被否决的方法。

没有原始依据时，不得补造决策原因。

### 4. EXPERIMENT_INDEX.md

建立跨实验线索引，至少包含：

- 实验 ID；
- 科学问题；
- branch；
- commit；
- 数据集与评估协议；
- 结果文件；
- 结果性质；
- 审阅状态；
- 与其他实验的关系。

重点解决“我记得做过这个实验，但是不知道在哪个分支和报告中”的问题。

### 5. tracks/*.md

针对 RT、FE、V01 等实验系列分别保存详细状态。

检查仓库后再确认最终分类，不要机械地按上述三个名字分组。

### 6. CHAT_HANDOFF.md

提供一个供新 ChatGPT 对话读取的精简入口。

目标长度：约 1,000–2,000 中文字。

包含：

- 最终科研目标；
- 当前主要任务；
- 活跃实验线及其准确状态；
- 近期最重要的可信结论；
- 未解决的关键问题；
- 下一步优先事项；
- 权威证据与文件入口。

这个文件是导航摘要，不是完整科研报告。

## 四、第三阶段：建立自动维护机制

编写轻量级 Python 脚本，例如：

`tools/ai_memory_check.py`

`tools/ai_memory_update.py`

其中：

**检查工具：**

- 检查 Markdown 文件和必要字段是否存在；
- 检查引用的仓库内文件路径；
- 检查 commit SHA 是否有效；
- 检查实验状态的格式；
- 检查重复实验 ID、决策 ID；
- 检查文档引用是否互相矛盾；
- 发现陈旧或无法验证的状态时报警。

**更新工具：**

- 从 Git 元数据和已有结构化记录提取可验证的信息；
- 协助生成 CURRENT_STATUS 和 CHAT_HANDOFF；
- 对科学结论只生成待审核草稿，不凭指标文件名自动推断结论；
- 保留人工维护的内容；
- 避免覆盖不同实验分支的状态。

不需要建立数据库、向量检索系统或复杂的外部服务。

## 五、第四阶段：接入 Codex 工作流

修改现有 `AGENTS.md`，加入少量必要规则：

1. Codex 开始任务时，读取项目记忆和对应实验线状态。
2. 检查状态文件与当前 branch/HEAD 是否一致。
3. 实验结果提交后，判断是否需要更新 CURRENT_STATUS。
4. 涉及重要科学决策时更新 DECISION_LOG。
5. 新实验或实验收尾时更新 EXPERIMENT_INDEX。
6. 生成或更新 CHAT_HANDOFF。
7. 在 CODEX-RESULT 中报告记忆文件更新情况。

保留现有 RT55 兼容性、安全规范、实验协议和交接格式。

不要全面重写 AGENTS.md。

## 六、第五阶段：历史对话接入

GitHub 中可能没有全部 ChatGPT 历史对话。

因此：

- 不要声称已经读取全部历史聊天。
- 优先根据 GitHub 已核验的报告和交接文档恢复历史。
- 对缺少原始讨论依据的重要决策，标记为 `needs_history_review`。
- 提供一个补录模板，让用户以后从旧聊天中提取缺失信息。
- 对来源有争议的内容保留多个来源及其差异。

不得把推测包装成用户以前明确做出的决定。

## 七、验收测试

至少完成以下测试：

### A. 新对话恢复测试

设计一个模拟场景：

新的 ChatGPT 对话不读取全部历史，只读取：

- PROJECT_MEMORY.md
- CURRENT_STATUS.md
- CHAT_HANDOFF.md

应当能够回答：

1. 项目的最终目标是什么？
2. 当前有哪些实验线？
3. 每条实验线分别做到哪一步？
4. 最新可信结论有哪些？
5. 哪些问题仍然没有解决？
6. 下一步应该优先开展什么？
7. 如何查找某个历史实验的原始证据？

### B. 追溯测试

随机选择至少五项历史技术决策或实验结论。

检查是否可以从项目记忆追溯到原始报告、配置、结果和 commit。

### C. 更新测试

模拟一次新的实验结果提交。

验证：

- 仅相关实验线被更新；
- 其他实验线的状态没有被覆盖；
- 历史决策不会无故消失；
- CHAT_HANDOFF 正确更新；
- 引用和链接检查通过。

### D. 安全回归测试

验证：

- 没有修改模型代码；
- 没有修改实验配置；
- 没有触发训练或超算任务；
- 没有删除原有报告；
- 没有覆盖用户未提交的工作。

## 八、交付物

完成后请提交：

1. 项目记忆文件；
2. 各实验线状态索引；
3. 维护与检查脚本；
4. 简要的 AGENTS.md 更新；
5. 一份使用说明；
6. `docs/ai/CODEX_RESULT_PROJECT_MEMORY_BOOTSTRAP.md`；
7. `docs/ai/CHATGPT_REVIEW_REQUEST_PROJECT_MEMORY.md`。

审阅请求应当包含：

- 实际使用的 repository/branch/base commit/result commit；
- 新增与修改的文件清单；
- 已恢复的历史范围；
- 仍缺少的历史信息；
- 所有测试结果；
- 模拟新对话恢复测试的问答；
- 如何日常维护；
- 是否允许开始归档旧聊天的建议。

将改动放在独立分支，例如：

`chore/project-memory-bootstrap`

推送 GitHub 后，提供完整 commit SHA。

不要自行删除任何 ChatGPT 对话，也不要删除 Git 历史。

## 九、完成标准

本轮成功的标准不是生成很多 Markdown 文件，而是：

**新 ChatGPT 对话能用最少的上下文准确理解当前项目，并且随时可以追溯重要历史。**

应避免重复维护、不一致快照、过度自动化和没有证据的结论。

请先审计现有机制，在复用已有工作的基础上实施最小必要修改。

开始执行，并在完成后提供结果和审阅入口。
